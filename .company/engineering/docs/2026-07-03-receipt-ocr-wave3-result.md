# receipt-scanner OCR精度改善 Wave3 実装記録（2026-07-03・Tier L）

## 概要
Wave3 = Stage2B で追加した新フィールド（tendered_amount/change_amount/tax_breakdown/tax_exempt_hint）に依存する検算ゲート群。設計方針＝**ログ観測先行**（本番でどれだけ発火するか＝正しいレシートを誤って手動確認に回さないかを実測してからハードゲート化）。

## ★重要な事前分析（全2034件正解＋新フィールド付き再OCR291件でオフライン評価）
Wave2 のプロンプト修正が誤りの源流を直したため、**ハードゲート候補の多くが冗長化・または昇格不可**と判明:

|---|---|---|
| **TAX-3(1)** desc⇔tax_code自己矛盾（split description が「8%」だが tax_code=136） | 全done中 23発火・TP15・FP8（35%） | **最高価値（誤登録15件捕捉）だが FP8件は税理士のテンプレ計上（小計→163/税額→136）＝TAX-5規約確定まで昇格不可** |

## 実装（api/process.js のみ・純粋追加・挙動完全不変）
`wave3Observe(parsed, resultJson, receiptId)` を新設し、resultJson 構築直後・ゲート判定前に呼ぶ。**status/DB を一切触らず** `logger.info('wave3-observe: ...')` で発火のみ記録:
- TAX-3.1_desc_taxcode_contradiction
- AMT-2a_tendered_change_mismatch（分割決済除外）
- AMT-2b_tax_breakdown_sum_mismatch（±2円超）
- TAX-6_tax_exempt_but_taxable

try/catch で本流を絶対に止めない。副作用ゼロ（`.update()`/`.from()`/status 変更を含まないこと grep 確認済）。build（tsc+vite）PASS。

## 運用（昇格ロードマップ）
1. **本番ログを `wave3-observe` で grep** し、v3.13b の実トラフィックでの発火率・分布を1〜2週間観測（オフライン評価は targets 偏りの291＋v3.11の2034なので実分布で再確認）。
2. **TAX-3(1)**: 税理士が TAX-5(1)「小計→163/税額→136 のテンプレ計上をやめ、印字税率通りに統一」を確定 → FP8件が真の誤りに変わり、error 化へ昇格可能（誤登録15→23件を登録前捕捉）。
3. **AMT-2(a)**: 発火が出て FP0 を維持するなら低リスクで error 化（お預り誤読の安全網）。
4. **TAX-6**: 非課税品（証明書代/切手/レターパック）の扱いを確認後に error 化（非課税は136/163で自動計上できないため手動確認が正）。
5. AMT-2(b)(c)・G3 は昇格しない（補助フィールド誤読/意味論破綻/プロンプトで解決済）。

## ★方法論の学び
- **プロンプト修正が下流ゲートを冗長化する**: 源流（プロンプト）で直せた誤りは、ゲート（下流）では発火しなくなる（G1/G3が0発火）。ゲートは「プロンプトで直せない残差」にのみ価値がある。
- **ゲート昇格は必ずオフラインで FP を実測してから**: 発火＝正しくないとは限らない（TAX-3のFP8はテンプレ計上、AMT-2cは意味論破綻）。正解データでFP率を測らずに error 化すると正しいレシートを手動確認に回す退行を生む。
- **ゲートは会計規約に依存する**: TAX-3(1) の可否は税理士のテンプレ計上規約次第。技術判断だけで昇格できない項目がある。
