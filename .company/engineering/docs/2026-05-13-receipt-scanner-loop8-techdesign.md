### 2.2 §1.10 新設「構造的ハイリスク様式・confidence 強制 medium」(挿入位置: 既存 L22「### 縦書きヘッダーの実例（v3.5 追加）」セクションの直前)

新規セクション。本文:

```
## 構造的ハイリスク様式 (v3.10 新設) — confidence 強制 medium

以下の物理的様式は OCR が桁ハルシネーション・空欄誤認・字形誤読を発生させる確率が
他様式と比べて顕著に高い。これらの様式に該当する画像では、たとえ読み取り結果に主観的
自信があっても confidence: "high" を申告してはならず、**必ず confidence: "medium"**
にして uncertainty_reason に該当様式名を明記すること。システム側で人間確認に振り分ける。

### 様式リスト (該当したら強制 medium)

1. **★ プレフィックス領収証 (青罫線手書き様式)**
   - 金額欄の冒頭に手書きの「★」マーカーが付された領収証 (コクヨ ウケ-1048 等)。
   - SABABA グループ内部発行領収証で典型的に使われる罫線青紙。
   - ★ は手書きの太さ・崩しにより「1」「Y」「X」「米」「米米」「半角 *」と誤読される。
   - 末尾「-」を「0」と誤読、罫線青紙のノイズで桁数判定がブレる。
   - **発動条件**: 金額欄の冒頭または金額の先頭に ★ / ☆ / ※ / 米 / X / * 等の **5 角形・星形・米印** マーカーが存在する場合。
   - **強制動作**: confidence: "medium" + uncertainty_reason に「★ プレフィックス手書き領収証様式のため桁ハルシネーション可能性あり」を必ず含める。

2. **罫線 grid 金額欄 (各桁縦線区切り)**
   - 金額欄が「| | | | , | | | |」のように各桁を縦線で区切った grid 様式。
   - 4 桁金額が grid 内に書かれる場合 leftmost grid が空欄になるが、境界線そのものが「1」と誤認される。
   - 逆に leftmost grid に薄く「1」が書かれている場合もあり、両方向の誤読リスクがある。
   - **発動条件**: 金額欄に各桁の縦罫線 (3〜7 本以上) が等間隔で並んでいる場合。
   - **強制動作**: confidence: "medium" + uncertainty_reason に「罫線 grid 金額欄のため leftmost 空欄/境界線誤読の可能性あり」を含める。
   - **二仮説比較**: 「leftmost grid が空欄」と「leftmost grid に薄く 1 が書かれている」の両方を仮説立てし、画像内の他箇所 (但し書き欄の数値・宛名「○○様」直後の数字・小計欄の本体額) と突き合わせて整合する方を採用する。整合できなければ medium 維持。

3. **縦書き店名 + 店名印字欠落レシート**
   - 店名が縦書きで印字されていて、なおかつ本文中に横書きの店名印字が無い様式。
   - 縦書きヘッダーが判読不能の場合、本文中の商品メニュー (餃子・炒飯・ドリンク等) から別チェーン店名を hallucinate しがち。
   - **絶対禁止**: メニュー品目名 (炒飯・餃子・ラーメン・カフェラテ・お通し等) から類推して「餃子の王将」「ラーメン花月」「カフェ・ベローチェ」等の **既存実在チェーン名を store に出力すること**。
   - **発動条件**: 画像上端・右端・左端のいずれかに縦書き文字列領域があり、それが判読不能と判定された場合。
   - **強制動作**: store: null + confidence: "medium" + uncertainty_reason に「縦書きヘッダーが判読不能。本文中の品目から類推による店名創作は禁止」を含める。

4. **金額欄 grid + ★ プレフィックスの複合様式**
   - 上記 1 + 2 が同時発動する SABABA 系青罫線領収証は最高リスク。
   - 二仮説 + 強制 medium を二重適用すること。

### 既存セクションとの関係

- §「自信度の自己申告 (v3.2 追加・必須)」(既存 L235〜) の確信度判定よりも本セクションは **優先** する。本セクションの発動条件に該当した瞬間 high → medium へ downgrade する。
- §「補強推論ルール (v3.9.4)」(既存 L256〜) の「複数の独立根拠」要件と二重適用する。複数根拠があっても本セクション該当なら medium 維持。
- process.js 側の v3.9.4 high-but-doubting gate (UNCERTAINTY_DENYLIST) で自動 error 化される運用に乗る。
```

### 2.3 §1.11 装飾カタカナ屋号の明文化 (挿入位置: 既存 L138「【店名形式の許容範囲・v3.9 追加】」内の bullet 「カナ・ローマ字混在屋号」直前)

既存「英字小文字屋号」「ひらがな屋号」「数字のみ屋号」のリストに以下を **新規追加**:

```
    - **装飾カタカナ屋号 (毛筆体・行書体・カリグラフィー・ロゴタイプ)** (例: `マンサルド`, `ミッドナイト`, `タカミヤ`, `ノマド`) — シーシャ・バー・カフェ・喫茶・スナック業態で頻出。屋号が装飾カナで印字され、その下に英語サブタイトル (例: "MIDNIGHT CLASSICAL CAFE MANSARDE") が併記されることが多い。**この場合、装飾カタカナ側を最優先で store に採用する**。英語サブタイトルを採用すること、カタカナをひらがなに置換すること (例: `マンサルド` → `まさるど`、`タカミヤ` → `たかみや`)、カタカナを漢字翻訳すること は全て禁止。画像に印字された装飾カタカナ文字列を **原文ママ** で採用する。装飾フォントによる字形の揺れにより字画判定に迷う場合は confidence: "medium" + uncertainty_reason 必須 (§「補強推論ルール」 v3.9.4 の単一根拠条項を適用)。
```

### 2.4 §1.12 多言語ロゴ vs 日本語表記の優先順位決定表 (新設) (挿入位置: §1.11 直後・既存 L146「確実に読み取れなければ null」の前)

```
### 多言語・ロゴ vs 日本語表記の優先順位決定表 (v3.10 新設)

ロゴ・社名が複数言語・複数表記で併記されている場合、以下の **2 軸決定表** で発行者を確定する。
直感的「大きい印字優先」「ロゴ最優先」を機械適用すると逆効果になるパターンが実在するため、
業態別・表記の組み合わせ別に決定論的に判定する。

**A 軸: 言語の組み合わせ別優先順位**

| 表記の組み合わせ | 採用優先順位 | 具体例 |
|---|---|---|
| カタカナ屋号 + 英語サブタイトル | カタカナ優先 | `マンサルド` + "MIDNIGHT CLASSICAL CAFE MANSARDE" → store: `マンサルド` (深夜喫茶マンサルド の場合は `深夜喫茶マンサルド`) |
| ひらがな屋号 + 英語サブタイトル | ひらがな優先 | `はまや` + "Hamaya" → store: `はまや` |
| 漢字屋号 + 英語サブタイトル | 漢字優先 | `鮨菊` + "Sushi Kiku" → store: `鮨菊` |
| 外国語ロゴ + 日本語カナ表記併記 | **日本語側優先** | `thalātha` (アラビア語/外国語ロゴ) + `サラーサ` (日本語カナ) → store: `サラーサ` |
| 英字大文字ロゴのみ (日本語併記なし) | 英字採用 | `apollostation` → store: `apollostation` |
| 英字小文字屋号のみ (日本語併記なし) | 英字採用 | `neighbor` → store: `neighbor` |

**判定根拠**: 日本国内で営業する店舗の正式登記・税務上の屋号は日本語表記が標準であり、
外国語ロゴ (アラビア語・タイ語・中国語等) は装飾用途であることが多い。一方カタカナ屋号 +
英語サブタイトルの組み合わせは日本のカフェ・バー業態の標準スタイルで、英語側はサブタイトルに
すぎない。したがって判定は「大きさ」「先頭/末尾」ではなく「**画面上で日本語表記が読めるなら
日本語側、日本語が一切無いなら外国語側**」とする。

**B 軸: 業態別優先順位 (ブランド店舗 vs 運営会社の混同回避)**

| 業態 | 採用優先順位 | 具体例 |
|---|---|---|
| ガソリンスタンド (GS) | **ブランドロゴ優先** (小さくても採用) | `apollostation` ロゴ + `出光リテール販売株式会社` → store: `apollostation` |
| GS (ENEOS 系) | **ブランドロゴ優先** | `ENEOS` ロゴ + `西日本フリート株式会社 土山SA上り` → store: `ENEOS` |
| コインパーキング (タイムズ24 系) | **運営会社優先** | `西横堀駐車場 第12号ブロック` + `タイムズ24株式会社` → store: `タイムズ24株式会社` |
| コインパーキング (その他) | **運営会社優先** | 施設名 + `パラカ(株)` → store: `パラカ(株)` |
| コンビニ・カフェチェーン | ブランド名優先 | `セブンイレブン` + 「株式会社セブン-イレブン・ジャパン」 → store: `セブンイレブン〇〇店` |
| 個人経営の飲食店 | 屋号印字優先 | 屋号 + 運営会社「合同会社XX」 → store: 屋号 (`neighbor`, `420`, `はまや` 等) |

**判定根拠**:
- **GS のブランドロゴ優先**: apollostation / ENEOS は **全国共通のフランチャイズブランド** であり、
  運営会社 (出光リテール販売 / 西日本フリート 等) は地域 FC 法人。会計仕訳上は全国ブランドで集約
  したいケースが多く、運営会社名で記録すると同一ブランドが複数法人名にバラける。
- **コインパーキング (タイムズ24・パラカ) の運営会社優先**: 駐車場は施設名 (西横堀駐車場・第12号
  ブロック等) が立地依存で頻繁に変わるのに対し、運営会社が会計仕訳上の発行者として一貫している。
- **GS とコインパーキングで逆ルールになるのはこの「会計仕訳の一貫性」基準** であり、業態判定が必要。
- 既存 v3.9.2 「駐車場運営会社優先ルール」(L636) はコインパーキングのみに限定するルールであった
  ことを本決定表で明文化した。GS には適用しない。

**衝突時の優先順位**: A 軸と B 軸が両方発動した場合は **B 軸を優先** する (業態判定が確定している
方が会計仕訳の精度に直結するため)。

**process.js 側との同期**: `normalizeStoreName` で `apollostation` / `ENEOS` / `タイムズ24株式会社` /
`パラカ(株)` は `replaceMode:'full'` で正規化されるため、prompt 側で運営会社名を出力しても本処理で
ブランド名に置換される (apollostation / ENEOS の場合) / 運営会社名のまま保持される (タイムズ24 /
パラカ の場合)。prompt 側ではこの決定表に従って **直接ブランド/運営会社を選んで出力すること** で、
正規化処理に依存しない決定論的挙動を目指す。
```

### 2.5 §1.13 カタカナ「エ」↔ ASCII「I」混同抑止 (新設) (挿入位置: §1.12 直後)

```
### カタカナ・ASCII 字形混同 mini-rule (v3.10 新設・パターン E)

印刷字の **カタカナ「エ」** は ASCII の **大文字「I」** と視覚的に酷似している。
レシート上部の店舗ロゴ / 印影 / 印字社名で「エ」を含む語が「I」「X」「k」 等の ASCII 1 文字
または別カナ「ス」「ク」に化けるケースが頻出する。

**典型例**:
- `株式会社パークエステート` (= Park Estate) → 誤読で `パークIステート` / `パークステート`
  (「エ」抜け落ち) / `パークスクエート` (「エ」→「ス」+「ク」) が発生。
- `エディオン` (家電量販店) → `Iディオン` / `ディオン` (「エ」抜け落ち) のリスク。
- `エクセル` / `エネル` / `エール` 等の「エ + 子音カナ」 開始語全般。

**強制動作**:
- 店名候補が ASCII 1 文字 (I, X, k, l, 1) を含む場合、それは **カタカナ「エ」の誤読**
  である可能性を必ず検討する。
- 「○○Iステート」「○○Xステート」「○○kステート」のような ASCII 1 文字を含む候補は、
  まず「○○エステート」へ置換した仮説を立て、画像内の他箇所 (住所欄・電話番号エリアの
  社名印字・領収書下部の発行者欄) で「エ」が読める根拠があれば「エ」を採用する。
- 同様に「○○ステート」(「エ」抜け落ち)・「○○スクエート」(「エ」→「スク」分割) も
  「エ」誤読仮説を優先検討する。
- 二仮説の判別が困難な場合は confidence: "medium" + uncertainty_reason に「印字カタカナ
```

### 2.6 §1.14 印字数字 8↔3 二仮説比較 (新設) (挿入位置: 既存 L122「**【高額金額起点の二仮説比較・v3.8 追加】**」の amount セクション末尾、L122 直後)

既存 v3.8 の「¥ 二仮説 (H1/H2)」ルールに **並列して** 「印字数字 8↔3 二仮説比較」を追加。挿入位置は既存 L122 直後・amount ルールの末尾:

```
    - **【印字数字 8↔3 二仮説比較・v3.10 追加】** 印刷字 (サーマル印字・レジ印字) でも、
      数字「8」と「3」は上半円形状が酷似しており、特に旧型サーマル印字のかすれ・滲み・
      解像度低下時に相互誤認が発生する。手書き ¥ 誤認 (v3.6/v3.8) とは別の独立した防御層
      として、以下を必ず実施する:
      - **発動条件**: 印字レシートで amount の **どこか 1 桁が 3 または 8** であり、かつ
        同じレシート内に **別の箇所で合計らしき印字** がある場合 (詳細レシート × 領収書
        併存型、または上部の手書き「合計欄」と下部の詳細レシート印字併存型)。
      - **二仮説並列比較の手順**:
        1. 採用した amount から、3 または 8 の桁を入れ替えた **対立仮説** を作る。
           例: `3420` → 対立仮説 `8420` / `3420` → 対立仮説 `8420` (3→8 / 8→3 両方向)。
        2. レシート画像内の **別の合計印字位置** (詳細部の「合計 ¥◯◯」・税区分サマリの
           合計・お預り/お釣り欄の合計) を探索し、対立仮説と一致するなら **対立仮説を採用**。
           例: 上部手書き欄に「¥3,420」と読めたが、下部詳細レシートの「合計 ¥8,420」と
           読めたら、3 と 8 の誤読疑い → 別の根拠 (詳細部) が一致する方 (8420) を採用。
        3. 別箇所の合計印字が見つからない、または両方とも 8 または両方とも 3 の場合は
           confidence: "medium" + uncertainty_reason に「印字数字 8↔3 の混同可能性あり、
           整合確認できず」を含める。
      - **判定基準 (除外条件・over-correction 防止)**:
        - 上部欄と下部詳細欄が **独立して同じ数字** を示している (両方とも 3 / 両方とも 8) なら
          元読みを維持する。
        - 「お預かり」「お釣り」「小計」「税抜本体」など合計とは別の数値印字を「合計」と
          誤って一致と判定しない。「合計」「ご請求金額」「お会計」「総額」「現計」のみと
          突き合わせる。
        - amount 全桁数が 1〜2 桁の小額 (¥100 未満) では発動しない。
      - **具体例**:
        - 肉のハナマサ実例: 上部手書き欄「¥3,420」/ 下部詳細レシート「合計 ¥8,420」併存 →
          二仮説比較で 3→8 採用 → amount: 8420。
        - 印字字形が両方とも明瞭で 3 / 8 のどちらも疑いない場合は元読みを維持。
```

```
  {"date":"YYYY-MM-DD","amount":4500,"store":"サラーサ","category":"交際費","tax_code":136,"confidence":"high","uncertainty_reason":""}
- 誤った出力例（絶対禁止）:
  - {"store":"thalātha", ...}
    → 外国語ロゴを採用。§1.12 A 軸「外国語ロゴ + 日本語カナ表記併記 → 日本語側優先」違反
  - {"store":"タラーサ", ...}
    → 「thalātha」を勝手にカタカナ転写した創作。画像に印字されていない文字列の出力は禁止
  - {"store":"サラーサ thalātha", ...}
    → 併記出力は禁止。日本語側のみ採用すること
- 判定根拠:
  1. §1.12 A 軸: 外国語ロゴ + 日本語カナ表記併記 → **日本語側優先** (apollostation のような
     英字ブランドロゴのみの場合 (= 日本語併記なし) とは逆ルールであることに注意)
  2. 日本国内営業店舗の正式登記・税務上の屋号は日本語表記が標準
  3. 複数の独立根拠 (本文末日本語印字 + 朱印内「サラーサ」) → §「補強推論ルール」 v3.9.4 を
     満たし high 可
  4. 屋号「サラーサ」は §「店名形式の許容範囲」 v3.9 のカナ屋号として正規屋号採用可
  5. category=交際費 の根拠は **店名 サラーサ ではなく** 但し書きと品目印字 (シーシャ + 飲食代)
```

### Few-shot 全体の整合性

- 既存 A〜L のスタイル (image 特徴 → 正しい出力 → 誤った出力例 → 判定根拠 の 4 部構成) を完全踏襲。

## §5 リスク分析

### 5.1 既存 Few-shot との衝突

- **A (はまや実例 → ひらがな屋号原文ママ)** vs **N (マンサルド → カタカナ屋号原文ママ)**:
  どちらも「装飾フォント屋号を原文ママで採用」という同方向ルールであり衝突しない。N は L (はまや) のカタカナ版という位置付け。
- **K (タイムズ24 → 運営会社優先)** vs **P (apollostation → ブランドロゴ優先)**:
  両者は §1.12 B 軸決定表で「業態別に逆ルール」と明文化しており、衝突しない。設計通り。
- **F (シモジマ → 縦書きヘッダー読む) / G (カルディ → 縦書き判読不能で null)** vs **O (縦書き + メニュー類推禁止)**:
  O は G の品目類推禁止条項を強化した位置付け。G は「null + medium」、O も「null + medium」で同方向。
- **既存 §「店名形式の許容範囲」(v3.9, L138)** vs **§1.11 装飾カタカナ追記**:
  既存 4 形式 (英字小文字 / ひらがな / 数字 / カナ・ローマ字混在) に「装飾カタカナ」を追加するだけで、既存形式の判定を変えない。後方互換。

### 5.2 enum 違反リスク

- 6 種類の category (`消耗品費・交通費・交際費・通信費・雑費・仕入高`) を逸脱する Few-shot は
  追加しない。M〜S の正しい出力例は全て 6 種類内で構成。
- tax_code は 136 / 163 の 2 値のみ使用。
- confidence は high / medium / low の 3 値のみ。

### 5.3 過剰 medium 化 (false positive of confidence downgrade) リスク

- §1.10 構造的ハイリスク様式の **発動条件** を具体化:
  - ★ 様式: 「★ / ☆ / ※ / 米 / X / *」マーカーが金額欄冒頭または金額先頭に存在する場合のみ
  - grid 様式: 各桁の縦罫線が 3〜7 本以上等間隔で並ぶ場合のみ
  - 縦書き様式: 画像端の縦書き文字列領域が判読不能と判定された場合のみ
- これにより通常のサーマル印字レシート (大半のコンビニ・スーパー・GS) は強制 medium 化されず、
  既存の high 通過率を維持。
- **想定影響**: SABABA 内部発行 ★ 領収証のみ強制 medium 化 → 月数十件程度の人間確認が必要だが、
  これらは多くが既存 `EXCLUDED_STORES` 該当 → 自動 error 化済の運用にそのまま乗る。

### 5.4 装飾カタカナ屋号の判定揺れ (false negative)

- 「装飾」の閾値が曖昧 → 通常カタカナ印字 (ゴシック体・明朝体) との境界判定がモデル依存。
- 緩和策: §「補強推論ルール」 v3.9.4 の「複数の独立根拠」要件を継続適用。単一根拠の装飾カタカナ
  は medium 維持 (Few-shot N で明示)。
- M〜S 全体で「装飾フォント・単一根拠は medium」ルールを反復刷り込み。

### 5.5 印字数字 8↔3 二仮説比較の過剰補正

- 全レシートで発動すると逆効果 (本物の 3 / 8 を誤補正する false positive)。
- 緩和策: 発動条件を「**画像内に別箇所の合計印字がある場合のみ**」に限定 (§1.14)。詳細レシート × 領収書併存型・上部手書き欄 × 下部詳細欄併存型などの特定様式のみ。
- amount 全桁数が 1〜2 桁の小額では発動しない。

### 5.6 多言語決定表 A 軸と B 軸の衝突

- 「apollostation (英字大文字ロゴのみ)」と「サラーサ (外国語ロゴ + 日本語カナ併記)」が
  A 軸の異なる行に該当する。
- 緩和策: A 軸の表組みで具体例を明示 (§2.4)。さらに「**A 軸と B 軸が両方発動した場合は B 軸を優先**」
  という衝突解決ルールを §1.12 末尾で明記。
- GS 業態判定 (B 軸) は給油明細 / 燃料種 / 登録番号 T などの強い業態シグナルから決定論的に判定可能。

### 5.7 process.js UNCERTAINTY_DENYLIST 拡張による false positive

- "確認済" / "OK" 等は実際の LLM 出力でも「迷いなしを示す placeholder」として使われている既存
  事例があるため、denylist に入れて空文字相当として扱うのは妥当。
- 真に「確認済 (実際に内部チェックを行った)」を示す reason が誤って空文字相当化される
  リスクは低い (実際に意味のある reason は具体的な迷い記述を含むため文字列長 > 10 文字程度になる)。

### 5.8 prompt サイズ増加によるトークン消費

- 現 prompt 727 行 → v3.10 で約 880 行 (約 21% 増)。
- ephemeral cache control が効くため (process.js L219)、cache hit 後の単位コストはほぼ不変。
- 初回 (cache miss) のみ約 2,000 トークン分の追加課金。Loop 8 deploy 直後の数件のみ影響。

### 5.9 後方互換性

- 既存 Few-shot A〜L、§1〜§3 の判定ルールは **削除・変更なし** (追記のみ)。
- 既存 v3.9.5 で done 状態の 71 件のレシートに対して再解析しても結果が変わらないことを期待
  (回帰テストとして smoke test 計画 §8 で検証)。

### 8.1 Phase 1: 16 件 (パターン A〜H 該当) 再解析

### 8.2 Phase 2: 既存 done 71 件の回帰テスト (サンプリング)

## §9 補足: 設計判断の根拠

### 9.1 「★ プレフィックス検出を process.js に追加しない」判断

検討案: process.js に「画像 metadata から ★ プレフィックス検出して confidence=medium 強制」を追加。

**見送り理由**:
- 画像処理 (OpenCV 等) を Vercel Functions で動かすのは ephemeral filesystem 制約 + cold start
  + bundle size のオーバーヘッドが大きい。
- prompt 側で「★ / ☆ / ※ / 米 / X / * 等の星形・米印マーカーを認識した場合に強制 medium」と
  指示する方が、Claude vision のマルチモーダル能力をそのまま活用でき、実装コストゼロ。
- LLM の vision 能力で十分検出可能 (v3.6 の手書き ¥ 認識と同レベルの認識能力)。

### 9.2 「Few-shot M〜S を 7 件にした」判断

- 8 パターン中、A と H は同一 Few-shot M で両方カバー (★ 様式 + 印字数字 8↔3 を組み合わせた
  リアルな事例として効果的)。
- B (装飾カナ) / C (縦書き類推) / D (GS) / E (カナ↔ASCII) / F (grid) / G (多言語) はそれぞれ
  独立 Few-shot として N / O / P / Q / R / S を追加。
- 既存 A〜L の 12 件 + 新規 M〜S の 7 件 = 19 件で十分な学習刷り込み。20 件超えると prompt
  サイズ膨張による cache miss 時コストが顕著化するため、ここで打ち止め。

### 9.3 「§1.10 構造的ハイリスク様式を新セクションにした」判断

- 既存 §「自信度の自己申告 (v3.2)」「補強推論ルール (v3.9.4)」と並列の **第 3 ガード** として
  独立セクションにすることで、prompt 全体構造の見通しが良くなる。
- ★ / grid / 縦書き / 装飾カタカナ などの **物理様式起点** の判定は、既存ルール (字形・字画起点 /
  根拠数起点) とは独立した次元であり、混在させると prompt が読みづらくなる。

### 9.4 「§1.12 多言語決定表を 2 軸構造にした」判断

- パターン D (GS = ブランド優先) と パターン G (多言語 = 日本語優先) は **逆方向のルール**
  であり、単純な「ロゴ最優先」「日本語最優先」では機械的破綻する。
- 業態 (B 軸) と 言語組み合わせ (A 軸) の 2 軸決定表にすることで、Claude モデルが決定論的に
  判定できる。
- B 軸優先の衝突解決ルールで、業態が明確に判定できる場合 (GS の給油明細・コインパーキングの
  入出庫時刻等) は業態判定を最優先する。

### 9.5 「印字数字 8↔3 二仮説比較を amount ルールに統合した」判断

- 既存 v3.6 手書き ¥ ルール + v3.8 二仮説 H1/H2 の延長線上で、印字字形誤読も同じ二仮説型
  ロジックで処理できる。
- 別箇所の合計印字との照合という発動条件で、過剰補正リスクを抑える設計。

## §10 まとめ

Loop 8 prompt v3.10 は、Loop 7 で確定した 16 件 8 パターンの OCR ミスを **prompt 側で根本解決** する。
process.js は最小変更 (UNCERTAINTY_DENYLIST 6 文字列追加のみ) で、既存 v3.9.4 high-but-doubting
gate を活用して構造的ハイリスク様式の自動 error 化を実現する。Engineer 4 並列 (A/B/D 同時起動、
C は B 完了待ち) で約 30〜40 分での Loop 8 deploy を目指す。Smoke test は 16 件再解析 + 既存 71 件
回帰テスト + 24 時間観察 + オーナー確認の 4 フェーズで実施。

**設計レビュー観点**: §7 P0 (10 項目) / P1 (7 項目) を Reviewer 集約時に必ず確認。
P0 1 件でも違反があれば差し戻し、P1 3 件以上の指摘で差し戻し。

**次フェーズ**: 本設計書を基に Engineer A〜D を起動 → Reviewer 集約 → Tech Lead 統合承認 → dual push。
